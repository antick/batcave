# Batcave Repository Instructions

This is the canonical repository guide for AI coding agents and human contributors. It applies to the entire repository. Tool-specific instruction files should point here rather than duplicate it.

## Start Here

Before changing files:

1. Read this file completely.
2. Read [`README.md`](README.md) for the short workspace overview and commands.
3. Use the requested task as scope; tracked ideas and documentation are not automatically authorized work.
4. Read recent commits with `git log -5 --oneline` to understand recent work.
5. Run `git status --short` and preserve unrelated or user-authored changes.
6. Inspect the relevant source files before proposing or implementing a change. This document is a map, not a substitute for the code.

## Self-Update Protocol (Mandatory)

Keep this file accurate as part of every task.

- If the repository differs from this guide, trust the current code/configuration, verify the behavior, and update this file in the same task.
- Update this file immediately when you discover a new architectural pattern, command, path, convention, dependency version, content type, integration, or source of truth that future agents need.
- When a task adds, removes, renames, or changes the responsibility of a file, route, component, collection, script, or package, update the relevant section here.
- Remove stale statements instead of appending contradictory notes. Keep this file concise and reference source files for volatile detail.
- Do not copy the whole guide into editor-specific files. Keep `AGENTS.md` canonical and make those files link to it.
- If no durable project knowledge changed, do not edit this file merely to create churn.
- Record completed work in a scoped commit, including documentation-only tasks.

If instructions conflict, follow this order: explicit user request, nearest scoped `AGENTS.md`, this root guide, then other repository documentation. Never weaken safety or data-preservation rules.

## Commands and Verification

Run commands from the repository root. Mise tasks select the pinned Bun runtime
and delegate to the existing package scripts; Bun remains the only package manager.

```sh
mise install
mise run install
mise run dev
mise run build
mise run preview
mise run quality
```

- `mise.toml` pins Bun to `package.json`'s `packageManager` version and exposes every root script except the internal `preinstall` hook. Keep both Bun pins aligned. Node 24 still comes from the host (for example, NVM).
- `mise run install` uses `bun install --frozen-lockfile`. Use `bun install` directly when deliberately updating dependencies and the lockfile.
- `mise tasks` lists available commands. Extra task arguments are forwarded to Bun, such as `mise run dev --host 127.0.0.1`. The direct Bun commands below remain valid.
- Root commands delegate to `@batcave/web` through Turborepo.
- Direct targeting: `bunx turbo run <task> --filter=@batcave/web`.
- `bun run build` is the required verification gate for code, content, configuration, routing, and dependency changes.
- For UI work, also run the dev server and inspect the relevant route through Astro's printed local URL, usually `http://localhost:4321`. Optional `DEV_HOST` in `apps/web/.env` binds another interface such as a Tailscale IP and allows that hostname in the Host header; that file is gitignored. Copy `apps/web/.env.example`. Do not commit machine addresses. With no `DEV_HOST`, Astro stays on localhost.
- Restart a long-running dev server after dependency or lockfile changes before verifying UI. Stale Vite optimization can break React island hydration (for example, `_jsxDEV is not a function`) even when the production build passes.
- `bun run quality` runs Biome formatting and linting, custom source-integrity validation, `astro check`, focused Bun tests, the production build, and rendered accessibility/link validation.
- `biome.json` is the formatting and linting source of truth. Astro full-file support is enabled; narrow overrides account for experimental Astro analysis, intentional utility-page autofocus, fixed-position heatmap keys, and the established CSS cascade. Keep `bun run validate:source` for repository-specific file-size, content, link-safety, and date checks that Biome does not replace.
- Focused tests use Bun's built-in test runner and live in `tests/` or alongside root validation helpers. There is no Playwright suite.
- Project artwork can be regenerated deterministically with `bun run artwork:projects`.
- For documentation-only edits, validate referenced paths/commands and run `bun run build` when the documentation claims or changes build/runtime architecture.
- Report verification commands and outcomes. If verification cannot run or fails because of unrelated work, say so explicitly.

## Architecture

### Rendering and page shell

- `apps/web/src/layouts/Layout.astro` is the root HTML shell. It imports global styles, emits SEO/structured metadata, derives non-article canonical URLs, requires page descriptions, and runs the pre-paint theme bootstrap.
- The root layout mounts Vercel Web Analytics through `@vercel/analytics/astro` only when `ENABLE_ANALYTICS` in `config.ts` is true. It is off by default.
- Astro renders the site statically. Use React only where browser state or interaction is required; keep content static Astro markup when hydration adds no value.
- `apps/web/astro.config.mjs` keeps HTML-aware whitespace compression enabled so Astro 7 preserves spaces between adjacent inline elements.
- `apps/web/src/components/SiteNav.tsx` is the shared navigation island. `apps/web/src/components/SiteFooter.astro` combines the intentionally reduced Home, About, and Contact `FOOTER_LINKS` from the shared navigation source with RSS and sitemap utility links.
- The footer shares `--deck-max-width` and responsive `--deck-side-padding` with the main container so their edges align. Its `potion.sh` credit link comes from `FOOTER_CREDIT` in `constants.ts`, independently of the template site URL.
- Shared navigation definitions live in `apps/web/src/lib/navigation.ts`. Blog is a direct link to the `/blog` category hub, with no submenu. Shelf is a direct link to `/shelf`, with Bookmarks, Wishlist, Movies, TV Shows, Reading, and Music as hub cards rather than extra top-nav items or a submenu. `apps/web/src/lib/navHelper.ts` discovers active blog categories for homepage, listing, sitemap, and search consumers.

### Home page

- `apps/web/src/pages/index.astro` fetches visible blog content and categories, builds dynamic navigation, derives the build-time stats, Now items, writing lists, and shelf cards, mounts `CardDeck` with `client:load`, and passes a static `IdentityCard.astro` slot.
- `apps/web/src/components/CardDeck.tsx` owns the single home-card shell and shared navigation, not the home content.
- The homepage identity wordmark uses `AUTHOR.firstName` then `AUTHOR.lastName` in title case (“Bruce Wayne”), as selectable text with natural wrapping. `typography.css` owns the self-hosted Pacifico family, natural 400 weight, and responsive display size. `identity-base.css` clips one continuous gradient across the full name, with solid-text fallbacks for printing and forced colors. Each theme’s coordinated tonal gradient lives in `themes.ts` and flow through the shared pre-paint and hydrated theme mapping.
- `apps/web/src/components/cards/IdentityCard.astro` stacks full-width `.home-section` blocks in this order: `HomeHero.astro` (profile, links, `HomeNow.astro`, and six stats), `HomeOpenSource.astro`, a `.home-split` row with `HomeWriting.astro` beside `HomeActivity.astro`, `HomeTopics.astro`, and `HomeShelf.astro`. Every section heading uses `HomeSectionHeader.astro` (`// label`, gradient divider, optional action link). Section styles live in `home.css` (shared shell, chips, tabs, links, GitHub heatmap), `home-hero.css`, `home-projects.css`, `home-activity.css`, `home-shelf.css`, and `home-responsive.css`.
- The Now card is derived in `apps/web/src/lib/homeNow.ts` from the spotlight project, the book count, and the latest post, so it never needs manual updates. Do not add hand-written Now items that can go stale.
- `HomeOpenSource.astro` shows the first `spotlight: true` project from `apps/web/src/lib/openSource.ts` as a full-width card (`HomeProjectSpotlight.astro`, with optional `install` command), then the remaining featured projects as a three-column tile grid. Kind filter chips come from `getOpenSourceKinds()` and toggle `hidden` on `[data-project-kind]` with a small inline script. Tiles clamp descriptions to two lines and keep repository and website icon links in the tag row so rows stay compact. Curated repository metadata, optional live-site links, and showcase copy live in `openSource.ts`.
- `HomeWriting.astro` offers Featured and Recent tabs. Featured shows up to `HOME_PICKS_MAX_COUNT` newest featured posts and links to `/featured`; Recent shows the same number of newest posts and links to all posts. Both use `HomeWritingLink.astro` and the shared `initTabs()` helper in `apps/web/src/lib/tabs.ts` (also used by `ContactDirectory.astro`).
- `HomeActivity.astro` pairs the GitHub heatmap with the twelve-month publishing chart and insights. `apps/web/src/lib/home.ts` derives the hero stats (Posts, Categories, Tags, Projects, Open source, Shelf items) and publishing data at build time.
- Only interactive leaves such as `TypingText.tsx` and `GitHubActivityHeatmap.tsx` hydrate; filters and tabs use small Astro inline scripts. Preserve this static/dynamic boundary.
- GitHub activity helpers live in `apps/web/src/lib/github.ts`. An empty `GITHUB_ACTIVITY_USERNAME` in `config.ts` selects clearly labeled, deterministic fictional activity from `sampleActivity.ts` without external requests. Configuring a username enables the live cached view; also update `GITHUB_PROFILE_URL`. Failed live refreshes show an unavailable state.
- Homepage topic chips come from visible post frontmatter and link into the shared Blog category routes; do not maintain a separate homepage category list.
- `HomeShelf.astro` pairs the book cover studies (`BookCoverStudy.astro`, compact) with one card per Shelf collection from `getSiteShelfCards()` in `apps/web/src/lib/shelf.ts`, which the `/shelf` page also uses. Empty collections show a Coming soon label instead of zero.

Shelf, Bookmarks, Wishlist, Movies, TV Shows, Reading, and Music mark Shelf as the active nav item. Home and resource cards share `.deck-wrapper` and `--deck-max-width` from `global.css`; below 768px the card is full width. Inner copy and blocks fill that card through `--page-content-max-width`. Do not reintroduce a narrower inner max-width on About, Contact, Bookmarks, Shelf, Wishlist, Movies, TV Shows, Reading, Music, Projects, listings, or article pages.

Books is the author page in the top nav, not the reading list.

Desktop keeps a sticky vertical rail beside the filtered grid; mobile uses a single non-wrapping swipeable row. `DirectoryShelves.astro` and `SubjectIndex.astro` render that layout. The grouped definitions in `apps/web/src/lib/directory.ts` generate shelves, icons, and bookmark records together.

- `/wishlist` is a Bookmarks-shaped resource page for things to get someday. Categories use real `/wishlist/[category]` routes and the shared subject rail when public items exist; dropped items stay unpublished. Data lives in `apps/web/src/lib/wishlist.ts`. Cards keep the note on-site and send outbound source links through `rel="noopener noreferrer"`.

Data lives in `apps/web/src/lib/music.ts`. `watch` and `listen` stay reserved so those retired URLs cannot become article slugs.

Movie and TV views split Want to watch above Watched. Reading splits Want to read above Read. Bundled titles and reviews are fictional. Reading keeps starter genre rails even when a genre is empty. Snapshot preference lists remain blog posts with optional `list` frontmatter; `ListArticleContent.astro` and `CuratedListItems.astro` render the same filterable item layout inside the shared post shell, with a Bookmarks-style sticky category rail on desktop and a single swipeable row on mobile. Movie and TV sample ratings live on the Shelf, not as public blog posts. The sample Bookmarks catalog includes Gotham, Public APIs, and Workshop categories with reserved example.org links.

- The Tags hub at `/tags` lists every tag used on visible posts with counts. Tag listings use `/tags/[tag]`, with pagination at `/tags/[tag]/page/[page]`. Helpers live in `apps/web/src/lib/tags.ts`. In-article tags link to those listings.

- Page titles using `.card-heading` must share the same responsive typography scale across resource, listing, category, and pagination pages.

### Content system

`apps/web/src/content.config.ts` defines one `blog` collection. Articles, code snippets, and reusable prompts live in year folders under `apps/web/src/content/articles/YYYY/`. Year-based storage is intentionally independent of category metadata, so recategorizing an article never requires moving it.

Unpublished working files live in `apps/web/src/content/drafts/`, which is outside the blog collection loader and therefore cannot generate routes or appear in navigation, search, RSS, or the sitemap. Start from `sample-draft.md`; when an article is ready, move it into the appropriate `articles/YYYY/` folder, finalize its metadata, and set `draft: false`.

All entries use the shared publishing/SEO schema: title fields, slug, dates, author, category/tags, featured/draft state, canonical and robots data, paired Open Graph artwork, schema/language data, and related slugs. Inspect the schema rather than copying its field list here.

- Visibility, draft labeling, featured/date sorting, related-content lookup, SEO types, and paired content imagery live in `apps/web/src/lib/content.ts`.
- Production always excludes drafts. Development visibility is controlled by `SHOW_DRAFT_CONTENT_IN_DEV` in `apps/web/src/lib/config.ts`. The same rule applies to project `draft` flags in `apps/web/src/lib/projects.ts`; `getVisibleProjects()` is the listing, search, sitemap, homepage-count, and detail-route source.
- Routes, navigation, search, RSS, and sitemap must all preserve draft filtering.
- Post detail routes use root-level `/{slug}` URLs. The Posts hub lives at `/blog`. All posts list at `/blog/all`, with pagination at `/blog/all/page/[page]`; categories list at `/blog/[category]`, with pagination at `/blog/[category]/page/[page]`. Do not add compatibility routes for the retired `/blog/page/[page]` listing URLs.
- Article path helpers, reserved root-level slugs, and reserved blog category ids (`all`, `page`) live in `apps/web/src/lib/articleRoutes.ts`; content validation prevents article slugs from colliding with static pages and article categories from colliding with listing routes.
- Root-level pages and articles share the same single-segment URL namespace. Before adding, renaming, or removing a top-level page, search article frontmatter for the proposed segment and update `RESERVED_ARTICLE_SLUGS` in the same task. The reserved list is explicit rather than automatically discovered. `tags` is reserved for the Tags hub. `featured` is reserved for the complete Featured writing page. `bookmarks` is reserved for the Bookmarks page. `directory` stays reserved so the retired `/directory` URL cannot become an article slug. `shelf`, `wishlist`, `movies`, `tv-shows`, `reading`, and `music` are reserved for those resource pages. `watch` and `listen` stay reserved so the retired URLs cannot become article slugs.
- A reserved article slug is a build-breaking content-schema error. Do not bypass the validation, silently rename content, or add compatibility routes; resolve the collision deliberately and verify it with `bun run build`.
- Build internal article links with `getArticlePath()` from `apps/web/src/lib/articleRoutes.ts`; do not reconstruct root slug paths in components or search code.
- Prompt articles use the optional structured `prompt` frontmatter object for a use case and usage details. `PromptArticleContent.astro` presents that context and preserves the prompt body as copyable preformatted text inside the shared blog detail shell. Prompt articles do not render a table of contents or related content.
- `apps/web/src/lib/headingIds.ts` assigns unique, emoji-free Markdown heading IDs through the native Sätteri processor before Astro collects the ToC. `astro.config.mjs` configures it with `@astrojs/markdown-satteri`; `tests/headingIds.test.ts` renders real Markdown through that configured processor. Visible heading text stays intact; ToC links use native browser anchor navigation; active-section lookup decodes URL fragments for non-English headings.
- Blog posts with h2 headings show the table of contents expanded by default in the right column. `BlogTableOfContents.astro` still allows collapsing it. Do not reintroduce a collapsed-by-default rail. The expanded list is capped to the remaining viewport height and scrolls internally, keeping the current section in view.
- List-style articles use the optional structured `list` frontmatter object for item layout and entries. `ListArticleContent.astro` renders those items with client-side filtering inside the shared blog detail shell. Helpers live in `apps/web/src/lib/listArticle.ts`. List posts default `showFeaturedImage` and `showRelatedPosts` to false so they skip the article featured image and related-content block; Open Graph images remain for social sharing. They use the header description as the only intro and do not render a markdown body above the list. List posts also omit reading time, tags, and published and updated dates.
- Article pages do not display a byline. Author remains in frontmatter and structured data only.
- Article prose keeps `width: 100%` within the responsive content layout so long code blocks scroll within the article instead of widening the mobile page.
- Every blog detail page fills the shared deck card (`--deck-max-width`). Do not reintroduce a narrower inner max-width for prompts, lists, TOC posts, or any other article format.
- Articles and projects use configured page sizes from `apps/web/src/lib/config.ts`.
- Blog categories are discovered automatically from visible post frontmatter and generate Posts-hub cards plus category routes. They are not top-navigation items. `POST_CATEGORIES` in `apps/web/src/lib/constants.ts` is optional metadata, icon, and description configuration, not an allowlist.
- Consolidated content formats use explicit subject-oriented `category` frontmatter. Snippets and prompts retain explicit `Snippets` and `Prompts` categories because their presentation format is meaningful; former notes use normal subject categories such as `Engineering` or `My Setup`.
- `apps/web/src/pages/rss.xml.ts` and `sitemap.xml.ts` generate feeds during the static build.
- Blog detail pages render their paired light/dark Open Graph artwork as the featured image below the article header using `ThemeAwareImage.astro`, unless the article turns that off.
- Article detail pages use a back link without a current-page crumb. Published date, updated date, and reading time sit on that same row as labeled values plus a reading-time chip. Tags render below the article body through `ArticleTags.astro`. List posts omit dates, reading time, and tags. Reading-time calculation lives in `apps/web/src/lib/content.ts` and its words-per-minute setting lives in `config.ts`.
- Optional article conversations use the structured `discussion` frontmatter object and `ArticleComments.astro`. X embeds are consent-gated: no third-party script or request is made until the visitor clicks to load comments, and the direct discussion link remains available as a fallback.
- Search is built in `apps/web/src/lib/search.ts`, emitted once as `/search-index.json`, and fetched by `SearchBox.tsx` only when the navigation search opens or the `/search` page is used.
- Sitemap entry policies and XML serialization live in `apps/web/src/lib/sitemap.ts`. Article routes use their real update dates for `lastmod`; static routes without a trustworthy source date omit it.

### Themes and brand

- Theme definitions, CSS-variable mapping, storage key, and default theme live in `apps/web/src/lib/themes.ts`.
- `apps/web/src/lib/themeUtils.ts` applies hydrated theme changes. Keep it aligned with the pre-paint logic in `Layout.astro` to prevent theme flash.
- First visits use Dark (`dark-theme`) at any time of day. The theme picker remembers the last choice in `preferred-theme`; both the pre-paint bootstrap and hydrated picker restore it, falling back to Dark when it is missing, invalid, or unavailable.
- `HangingBats.astro` mounts once from the shared layout and renders two upside-down SVG bats in the empty side margins on all four dark variants: at rest, wrap paths cover the body; open-wing paths scale from each shoulder (the right half mirrors the left), and only drawn shapes are hover targets. Sizes, hanging heights, and burst timings live in `lib/bats.ts`. `hanging-bats.css` derives gutters from `--deck-max-width`, caps each bat at the gutter width minus 8px so spread wings stay clear of the content, and hides the bats below 1360px, on light themes, in print, and in forced colors. Hover opens the wings without moving the hanging point. `lib/batMotion.ts` uses one idle timeout to choose a random bat every 14–32 seconds for a brief two-beat CSS-transform flap. Scheduling stops when the document or decorations are hidden or reduced motion is enabled. Hover is instant with reduced motion. Keep this document-scoped controller free of polling and per-frame JavaScript; the former flying effect and pause UI stay removed.
- `apps/web/src/lib/accessibility.ts` owns browser accessibility preferences such as reduced-motion-aware scroll behavior; `motion.css` provides the matching site-wide CSS treatment.
- Brand logo/favicon paths live in `apps/web/src/lib/brand.ts`; paired assets are in `apps/web/public/`.
- Project detail artwork keeps its natural aspect ratio at full width; do not cap image height or crop it with cover sizing.
- Every project uses distinct paired SVG artwork in `apps/web/public/images/projects/`; `scripts/generate-project-artwork.ts` is the reusable source for those assets.
- Keep the shared `ThemeAwareImage.astro` visibility selectors specific enough to override image-layout rules in consuming cards and hero containers, so exactly one theme source renders.
- The root canvas uses the live theme CSS variables so macOS overscroll follows theme changes; keep fixed initial colors out of the bootstrap.
- Do not hardcode theme values, storage keys, brand paths, or site URLs in components.

## Engineering Rules

### Scope and preservation

- Commit completed work automatically at the end of every task (see Task Completion Checklist). Never push, open a PR, deploy, or publish unless explicitly asked.
- Do not delete, overwrite, revert, format, or stage unrelated user changes.
- `.playwright-mcp/` contains disposable browser automation logs and snapshots; keep it ignored and out of commits.
- Diagnose before editing when the user asks to check, review, or explain.
- Treat ideas in documentation as context, not permission to implement them.

### Reuse and file size

- Prefer existing components, utilities, data modules, CSS classes, and patterns.
- Extract shared code before duplicating a structure or behavior across pages.
- Keep code files at or below 500 lines in general. If a touched code file exceeds 500 lines, split the relevant responsibility into focused modules/components. Documentation, generated files, lockfiles, and content prose are exempt.
- Do not grow oversized legacy files as a shortcut.

### Public-facing copy

- Write clear, direct American English with a calm, personal tone. Prefer specific claims and concise, useful descriptions over promotional language. Keep Gotham sample stories playful, original, and clearly fictional, as required under Template content.
- Use title case for page, article, project, and list titles. Use sentence case for descriptions, summaries, actions, and supporting labels. Avoid trailing punctuation in short navigation labels, tags, and buttons.
- Use consistent terminology across visible copy, metadata, and search text. Use `X` and `Discord` for those platforms, and preserve established product styling such as `Batcave` and `Astro`.
- Preserve URLs, published slugs, and asset filenames unless the task explicitly renames them; spelling cleanup alone does not justify renaming them. Interface dates follow the shared formatter rules below.
- Use the serial comma. Never write em dashes anywhere in the repository, including copy, docs, code comments, and page titles. Prefer a colon, comma, parentheses, or a new sentence. Separate page-title parts with ` - `, for example `Contact Bruce Wayne - ${SITE_NAME}`.

### Visual and typography consistency

- Before styling new UI, inspect the adjacent rendered elements and the shared rules in `Layout.astro`, `typography.css`, and the relevant focused stylesheet. Match the established hierarchy, spacing, color, opacity, and responsive behavior.
- Reuse an existing semantic typography class or shared `--font-size-*` token whenever the new text has an existing visual peer. Do not introduce a one-off font size for equivalent copy. Maple Mono is the site text family; the homepage name uses the Pacifico `--font-display` family (self-hosted Latin 400 via `@fontsource/pacifico`). Use `--font-size-body` / `--font-size-home-copy` for copy, `--font-size-card-title` / `--font-size-post-title` for card titles, `--font-size-section-title` for section headings, `--font-size-page-title` for page headings, `--font-size-ui` / `--font-size-chip` for controls, and `--font-size-meta` as the smallest allowed size for dense data.
- Compare new text against its immediate neighbors at desktop and mobile widths. Supporting copy must not visually overpower the titles or primary content it describes.
- `typography.css` owns typography tokens and all semantic font-size assignments, grouped by role, and loads with the render-blocking site CSS. Add equivalent selectors to its existing role groups rather than assigning font sizes in component styles. Recent writing, Featured writing, blog cards, and search results share writing-title and item-metadata sizes and line heights. Component styles keep layout, color, and decoration; icon and book-cover artwork sizing can remain local. Inline links, dates, and code inherit their surrounding text size. Do not duplicate font rules in `Layout.astro` or apply global `!important` font overrides.
- The default scale is 14px body, 12px UI/chips, 11px metadata, 16px card/post titles, and 20px section headings, expressed in rem. Page titles share `--font-size-page-title` (22–30px); the home identity uses `--font-size-display` (40–54px, scaled for its script letterforms). Keep reading and control sizes stable on mobile. Book-cover artwork and icons retain their own visual sizing.
- For muted secondary copy on the home identity card, reuse the established home-copy treatment (such as `.identity-contact-msg`) unless the design genuinely requires a new reusable variant.
- For every visual change, verify the rendered page (not only the build) and explicitly check font size, weight, line height, contrast, spacing, wrapping, and alignment against neighboring UI.

### Constants, imports, and dates

- No magic strings, numbers, URLs, storage keys, or configuration in page/component logic. Put site-wide values in `lib/constants.ts`, domain-specific data in its existing module, and theme values in `lib/themes.ts`.
- Keep all static imports at the top of JS/TS/Astro frontmatter. Do not use dynamic inline imports inside functions.
- Render UI dates only through `formatDate()` or `formatDateShort()` from `lib/utils.ts`. Add a reusable formatter there for any new format.

### Dependencies

- Use Bun, never npm, pnpm, or Yarn.
- Pin every dependency exactly; never use `^`, `~`, tags, or unpinned Git references.
- Keep audited transitive security pins in the root `package.json` `overrides` field so Bun applies them across every workspace.
- Select the newest stable version that was published at least two full days ago. Verify the publication date before changing a dependency. `bunfig.toml` enforces the 172800-second minimum age during dependency resolution. Bun preserves existing locked resolutions, so also check the publish dates of newly locked versions after an upgrade.
- Keep TypeScript on the newest compatible 6.x release while `astro check` requires its programmatic API; TypeScript 7 currently fails this check.
- After dependency changes, run `bun install`, include `bun.lock`, and run `bun run build`. The React integration uses the Oxc-based v7 pipeline with plain `react()` configuration; no Babel options or opt-in React Compiler are configured.
- In the final summary, name each added/updated version, say whether it was the latest stable release, and explain when a newer release was rejected for being under two days old.

### APIs and backend code

- The project currently has no API endpoints, backend, database, or `openapi.json`.
- If an endpoint is introduced, create and maintain a root `openapi.json`; update it for every endpoint addition, change, or removal.
- Wrap dependent database writes in a transaction.
- If Drizzle ORM is introduced, use its query builder rather than raw SQL.

### Security and CI

- Never add a GitHub Actions `pull_request_target` workflow.
- Never use shared caches in publish or release pipelines.
- Do not expose secrets or private resume data. Demo social links must use official platform homepages rather than invented personal accounts. Fictional product links use example.org.
